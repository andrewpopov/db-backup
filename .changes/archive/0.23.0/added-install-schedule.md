kind: added
summary: New `db-backup install-schedule` writes an app's backup schedule from its repo into the invoking user's crontab
---

The schedule lives in `db-backup.schedule.json` (`--config <path>` overrides): a `name`, an absolute `cwd`, and `jobs` with an `id`, a 5-field `cron`, a `command`, an absolute `log` and an optional `after` that must run strictly later than the job it names. It writes one `# db-backup:<name>` block, each job rendered as `cd '<cwd>' && ( <command> ) >> '<log>' 2>&1`, replaces an existing block in place, and a rerun with no change writes nothing. `--replace-line <substring>` and `--replace-block <start>=<end>` migrate an old unmarked line or marked block and are safe to keep in a deploy hook: zero matches is a warning once the block is installed and an error before, two or more always fail, and a match inside any marked block, a comment or an environment line never counts. The new block takes the first removed item's position so it does not inherit a mid-file `PATH=`. It refuses root, a `cwd` or log directory that is missing on a real install, duplicate, unpaired or nested markers, a crontab with escaped control characters, a crontab that changed while planning, an unescaped `%` or a word-leading `#` in a command; `TZ=`/`CRON_TZ=` lines warn, or fail with `--strict`. `--dry-run` prints a diff and writes nothing; `--json` prints the result. `installSchedule`, `validateSchedule`, `renderScheduleBlock` and the pure `replaceCrontabBlock` are exported.
